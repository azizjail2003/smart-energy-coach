# Stage 1 Handoff: EnergyReading

## Summary

Stage 1 establishes the `EnergyReading` data contract for Subsystem 1, Energy Simulation and Analytics. The model is a Python dataclass containing one timestamp, device identity, energy measurement, room temperature, carbon dioxide measurement, and sustainability score. It provides validation before database writes and a standard dictionary representation for Subsystem 2 web templates.

The UML name `score` is also supported through a read-only property. The stored field remains `sustainability_score`, matching the MySQL schema and Subsystem 2 templates. Every reading is also scoped to a campus `building_id`, defaulting to `library`.

## Data Contract

| Attribute | Python type | Physical unit | MySQL column |
| --- | --- | --- | --- |
| `timestamp` | `str` | Date and time, formatted `%Y-%m-%d %H:%M` | `timestamp` (`DATETIME NOT NULL`) |
| `building_id` | `str` | Campus building identifier; default `library` | `building_id` (`VARCHAR(50) NOT NULL`) |
| `device_type` | `str` | Device category | `device_type` (`ENUM('Heating','Lighting','Servers','Other') NOT NULL`) |
| `kwh` | `float` | Kilowatt-hours (kWh) | `kwh` (`DECIMAL(6,2) NOT NULL`) |
| `room_temp` | `float` | Degrees Celsius (C) | `room_temp` (`DECIMAL(4,1) NOT NULL`) |
| `co2_kg` | `float` | Kilograms of CO2 (kg) | `co2_kg` (`DECIMAL(6,2) NOT NULL`) |
| `sustainability_score` | `int` | Score from 0 to 100 | `sustainability_score` (`INT NOT NULL`) |

The MySQL `id` column is generated by the database and is not part of the Stage 1 dataclass. Subsystem 1 persists and queries through Subsystem 3's MySQL repository interface, with an isolated local repository fallback for offline tests.

## Validation Guards

`EnergyReading.validate()` returns `True` only after all four guards pass. It raises `ValueError` with a specific message as soon as it finds invalid data.

1. **Non-negative energy:** `kwh` must be at least `0`. Negative consumption is physically invalid and would distort totals, comparisons, and efficiency calculations.
2. **Realistic room temperature:** `room_temp` must be between `0.0` and `45.0` degrees C, inclusive. Values outside this range are unlikely for the monitored rooms and usually indicate a sensor or input error.
3. **Known device type:** `device_type` must be one of `config.DEVICES`: `Heating`, `Lighting`, `Servers`, or `Other`. This prevents orphan categories from entering MySQL and keeps analytics grouping consistent.
4. **Valid building identifier:** `building_id` must be a non-empty string. This prevents readings and alerts from being assigned to an unusable or ambiguous campus scope.

Rejecting invalid records before insertion protects the `energy_readings` table from bad measurements. MySQL enforces required columns through Subsystem 3's repository, but application-level validation is needed for these domain rules and building isolation.

## `to_dict()` Example

A valid reading such as:

```python
EnergyReading(
    timestamp="2026-10-28 14:30",
    device_type="Lighting",
    kwh=12.5,
    room_temp=22.0,
    co2_kg=4.75,
    sustainability_score=86,
    building_id="library",
).to_dict()
```

produces this exact dictionary structure for Subsystem 2 templates:

```python
{
    "timestamp": "2026-10-28 14:30",
    "device_type": "Lighting",
    "kwh": 12.5,
    "room_temp": 22.0,
    "co2_kg": 4.75,
    "sustainability_score": 86,
    "building_id": "library",
}
```

The `score` compatibility property is intentionally not included because `asdict()` serializes dataclass fields, while `sustainability_score` is the database and template contract.

## Stage 2 Preview

Stage 2 will add `ScoreCalculator`, a pure math engine that calculates sustainability scores from validated energy readings. It will consume the Stage 1 model without handling database access or web rendering, keeping score logic independently testable and making the score formula explicit for review.
